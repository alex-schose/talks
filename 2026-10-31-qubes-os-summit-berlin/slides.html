THE PROBLEM

Agents want broad powers.
Qubes isolates by denying them.

  • on the host, with full access — Mac, Windows, Linux
  • in one qube: the smaller dom0 surface, granted — but it cannot create a qube, choose a network or build a template
  • so it gets widened by hand, unrecorded — here every widening is a proposal or a dialog

Not as safe as an agent with no powers.
The safest way I know to give it real ones.

WHAT IT IS

MCP is the standard way an AI app — Claude, or a model you host — calls tools.

qubes-mcp makes Qubes one of those tools.

  • an agent can create qubes, build templates, run commands and move files
  • every call goes to dom0, and dom0 decides it
  • anything sensitive waits for you to accept it, in dom0
  • qubes outside the agent's space are invisible to it

HOW IT WORKS

Four rules

  1. dom0 decides every call. Every tool is a qrexec call; the caller is the only identity.
  2. The hub acts inside AI space. Only you widen it. It is root in every managed qube, templates included. Projects, leads, a lead's firewall, packages for a guarded template and windows on guarded qubes are proposals you accept.
  3. A project sees nothing outside itself. Workers call no qmcp service and cannot reach their lead or the hub.
  4. Nothing leaves a project without your dialog. One exception: its dump sink — a qube outside AI space its workers can drop files into, and no agent can open.

TWO THINGS QUBES-MCP ADDS

One agent runs the whole lab

A proxy qube you can build by hand. What is new: one agent builds the proxy, runs the app under test behind it, and reads the capture — coordinating both sides in real time.

An agent with no network

The control channel is qrexec, not the network. A local model in a qube with no network can serve a lead that has none either — proven with a toy model; real work needs a far bigger one.

WATCHING AN AGENT

New in 1.2: a project's AI builds proxies for its own members. Root in a proxy can lift its clients' firewall rules; the topmost proxy's rules still hold them.

BACKUP · ISN'T THIS DOM0 ATTACK SURFACE?

Yes. About 27,000 lines of it, all within the hub's reach.

  • one fail-closed check behind every service; identity is the qrexec caller, nothing else
  • requests over 64 KiB refused before they are parsed; at most 8 concurrent calls for the hub, 4 for a lead
  • a static rulebook — nothing writes the policy at run time
  • a qube outside AI space costs the same qubesd calls as a missing one

This is the part I most want read.

Not on that log: command execution, copy-out and firewall writes — they go straight to the qube or the Admin API, not through qmcp's code. dom0's journal still records each call: caller, service, target.

BACKUP · MAINTAINING TEMPLATES
dom0$ sudo qmcp open anon-debian-13 --for 2h # for up to 2h the hub runs commands in it as root dom0$ sudo qmcp seal anon-debian-13
  • a guarded qube is sealed: the rulebook refuses the hub every way in
  • a window lasts at most 24h; --firewall also lets the hub write its firewall rules
  • it ends on its timer, at every boot, or on seal — which kills what the hub left running
